# Durable invoice dispatch and period-close fencing

Invoice sends and successful payment/refund events now set `Invoice.FinanceDispatchPending` in the same conditional repository save as their immutable workflow payload pointer. The payload is the durable event log, and Finance journal `(SourceType, SourceId)` fingerprints are its acknowledgments. This avoids a separate queue publish after source commit that could lose a financial event. Older source records without the marker remain available through explicit invoice reconciliation.

`FinanceInvoiceWorker` scans pending source records every 15 seconds, at most 250 per pass. It runs by default and can be suspended with `Finance:InvoiceDispatch:Enabled=false`; suspension preserves pending markers. The worker requires no employee impersonation or Finance permission bypass endpoint. It validates tenant partition, source ID, payload path and canonical Customer before applying the same deterministic posting function used by operator reconciliation.

Finance commits before the source marker is acknowledged. A crash or ambiguous failure after the ledger commit leaves an event pending, and identical redelivery returns the original journal without posting twice. Conflicting content for an existing source key fails rather than rewriting history. A closed period, missing mapping, invalid customer or stale Finance version leaves the source pending with a bounded diagnostic and retry timestamp. Failed sources back off for 30 seconds; another source can still progress. Worker failures are logged. Finance-authorized reads can retrieve pending/blocked counts and source references through `FinanceInvoiceDispatch.GetStatusAsync`.

Invoice draft create/edit/send/delete and payload commits, plus Finance close/invoice-reconciliation/cutover acquire the same per-tenant Azure Blob lease in `finance-source-locks/{tenantN}/invoice-source`. The lease is deliberately infinite: an expiring mutex can permit a suspended writer to resume after a different process closes the period. Close holds this fence while reading source events, reconciling them, checking controls and saving the closed Finance state. A waiting invoice writer then reads the committed physical source version and period state before it persists a new event. Sending additionally checks persisted line amounts against the stored server totals, so a partial draft write cannot become an inconsistent posted source. Once Finance is initialized, new sends and successful cash events require an open period. Draft editing, signatures and reminders do not create a new financial posting date.

An orphaned lease after process termination **blocks further source commits and close**. Recovery is an explicit storage operation: stop every writer/worker instance, confirm no source or Finance operation remains active, inspect pending sources and ledger state, break the specific tenant's blob lease, then restart and reconcile. Never break a lease merely because another request waited 20 seconds. No automatic lease expiration or automatic break is implemented. Provision blob create/read/lease/release access along with the existing workflow and Finance storage access; use separate credentials for administrative lease recovery. A release failure is surfaced rather than silently allowing later operations through an uncertain fence.

For a migration cutover, suspend dispatch during onboarding and keep source operations frozen until the opening import commits; otherwise a newly initialized open period could legitimately post queued invoices before the migration is imported. Original invoices and payment events dated on or before the recorded cutover are already represented by imported opening AR and are not posted again. The cutover date is inclusive: new financial source events after import must have dates later than cutover, even if the old period is open. Post-cutover activity on historical invoices requires the canonical imported invoice AR item and matching Customer/Job identity. Operational invoice balance reads use the Finance AR balance plus source events still awaiting dispatch. They do not invent historical cash paid from a remaining-balance import.

The dispatcher streams fresh physical Invoice envelopes in pages of 100 to discover markers, bypassing general repository caches. It retains only the 250 oldest-attempted eligible sources while streaming the complete scan, so repeatedly blocked or uninitialized tenants cannot starve sources later in storage order. Uninitialized and coordination-failed sources retain their markers and record an attempt for fair retry selection. Because the marker lives inside the transactional JSON envelope, discovery still scans rather than querying a separate pending index. This provides durability but does not introduce a separately indexed queue or claim large-volume throughput. Load testing and an indexed dispatch discovery mechanism are still appropriate production scale work. Real provider delivery, cloud IAM, multi-instance termination/recovery and a production cutover rehearsal remain environment validation; local invariant and Azurite lease tests do not replace those checks.
